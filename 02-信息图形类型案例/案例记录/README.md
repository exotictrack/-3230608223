# 案例记录说明

此目录用于逐图分析的 Markdown 文件；图片在同级 `../案例图/` 内，**不得放到 `01-信息图形数据逻辑/`**。

## 后续案例更新规则：仅更新现有 Markdown 文件

用户已明确要求：**每次更新直接修改原文件，不新增任何 Markdown 文档或版本副本**。

1. **已有案例（CASE-0001–0016）**：直接编辑原 CASE Markdown 的 A–E 结论、来源、图片引用与修订记录；文件名和 CASE ID 不变。
2. **全新案例**：分配新的、不重复的 CASE ID；在现有 [案例索引](../案例索引.md) 追加案例记录，在相关的**现有表现类型说明文档**增添观察、分析与证据。**不创建新的 `CASE-xxxx.md`**。
3. 用[案例分析模板](../案例分析模板.md)中的 A–E 维度作写作规范，但直接填写到现有文档相应段落中，不复制模板生成新文件。
4. 如确有图片且具备适当使用许可，可将图片放入现有 `../案例图/` 目录并更新原文链接；**不得把图片放到 `01-信息图形数据逻辑/`**。
5. 只在案例证据支持时更新 `../../01-信息图形数据逻辑/` 中**现有的五份概念定义**；链接到现有案例索引或已有的 CASE 文件，并写清证据状态。
6. 检查原有链接、历史 CASE ID、内容重复及版本记录；使用 `python ../../scripts/validate_repo.py` 校验并提交到 Git，**不建立“修订版”文档**。

## 不可省略的证据纪律

- **观察事实 / 解释性判断 / 建议方法**要分开写；图内不可读的具体数字不得猜测。
- 一个案例可能有多种合理分类，主次都可记录，但不应每出现一个标签就算一个独立样本。
- 新发现的“设计方法”先标记**案例特征**，累积多种不同作品之后才能升级为通用原则。
- 同一原则有反例时保留反例并注明适用边界，不可直接删除不利样本。
- 不能从用户提供的图片擅自推断作者身份、制作动机和原始数据采集方法。
